FIX #1 — PMS "Request WO" Button (CRITICAL)
FILE: frontend\src\pages\inventory\PMS.tsx
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  The "Submit WO Request" button in the RequestWoModal component called
  setSubmitted(true) — this only toggled a local state variable to show a
  fake success screen. No HTTP request was ever sent. The Work Order was
  never created in the database.

WHAT THIS MEANS:
  Any mechanic or service adviser trying to request a Work Order from the
  PMS page would see "WO Request Sent" but nothing would appear in the
  Work Orders list. The entire maintenance initiation workflow was silently
  broken from the PMS side.

WHAT WAS CHANGED:
  - Added import: workOrderApi from '../../api/workOrders'
  - Added a useMutation hook that calls:
      workOrderApi.create({
        bus_id:      bus.id,
        description: notes,    ← comes from the WO Description field
        priority:    priority,  ← comes from the Priority Level selector
        type:        'preventive'
      })
  - The Submit button now calls mutation.mutate() instead of setSubmitted(true)
  - On success: invalidates ['work-orders'] cache, THEN sets submitted=true
                to show the success screen (now reflects reality)
  - On error: shows toast.error with the backend's error message
  - Button shows a loading spinner while the request is in-flight

RESULT:
  Clicking "Submit WO Request" in PMS now actually creates a Work Order in
  the database. It will appear in the Work Orders (W.O) page immediately.

FIX #3 — Dead Fleet API Declarations
FILE: frontend\src\api\fleet.ts
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  The fleet API file declared two functions that point to backend routes
  which do not exist in api.php or BusController.php:
    fleetApi.getMaintenanceHistory(id) → GET /buses/{id}/maintenance-history
    fleetApi.getPmsStatus(id)          → GET /buses/{id}/pms-status

WHAT WAS CHANGED:

    //  Those backend routes do not exist in api.php or BusController.
    //  Implement backend routes before re-adding."

RESULT:

  before trying to use those features.

FIX #4 — Fleet BusModal Driver Dropdown (Efficiency)
FILE: frontend\src\pages\inventory\Fleet.tsx
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  The driver dropdown in the BusModal (Add/Edit Bus form) fetched ALL users
  from the database, then filtered client-side:
    queryFn: () => userApi.list()
    drivers = users.filter(u => u.role === 'driver' || u.department === 'fleet')
  This wastes bandwidth and memory, sending all user records over the network
  just to filter most of them away in the browser.

WHAT WAS CHANGED:
    queryKey: ['users', 'drivers']
    queryFn: () => userApi.list({ role: 'driver', per_page: 999 })
    drivers = usersRes?.data?.data ?? []

  The UserController already supports role-based filtering server-side,
  so this is a straightforward improvement.

RESULT:
  Only driver-role users are returned from the API. Faster, leaner,
  and consistent with how Overview.tsx fetches drivers.

FIX #5 — Trip Tickets Query Key Mismatch (Cross-Page Cache Invalidation)
FILE: frontend\src\pages\logistics\Overview.tsx
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  React Query uses query keys to cache and invalidate data. When a mutation
  runs (e.g. approve a trip ticket), it calls:
    queryClient.invalidateQueries({ queryKey: ['trip-tickets'] })
  This tells React Query to re-fetch any query whose key starts with
  ['trip-tickets'].

  Overview.tsx was using: queryKey: ['trip-tickets-all']
  TripTickets.tsx was using: queryKey: ['trip-tickets']

  These are different keys. So:
  - Approving a trip in Overview did NOT refresh TripTickets.tsx list
  - Creating/updating a trip in TripTickets did NOT refresh Overview.tsx

WHAT WAS CHANGED:
  In Overview.tsx, changed:
    queryKey: ['trip-tickets-all']
  To:
    queryKey: ['trip-tickets']

  Added a comment: "same queryKey as TripTickets.tsx for cross-page invalidation"

RESULT:
  Any create, update, or approve action on either page now correctly
  invalidates and refreshes both the Overview and TripTickets data.

────────────────────────────────────────────────────────────────────────────
FIX #6 — Job Orders GeneratePO Supplier Filter (Accreditation Rule)
FILE: frontend\src\pages\procurement\JobOrders.tsx
────────────────────────────────────────────────────────────────────────────

PROBLEM:
  The "Generate Purchase Order" modal in Job Orders showed ALL suppliers in
  the dropdown, including blacklisted and pending ones. The business rule
  states only accredited suppliers may receive a PO.

  The backend (StorePurchaseOrderRequest.php) already validates this server-
  side, but allowing non-accredited suppliers to appear in the dropdown
  causes a confusing experience — the user selects a supplier, submits, and
  gets an error from the server.

WHAT WAS CHANGED:
  Query changed from:
    supplierApi.list({ per_page: 100 })
  To:
    supplierApi.list({ accreditation_status: 'accredited', per_page: 200 })

  Placeholder text changed from:
    "Select a supplier..."
  To:
    "Select an accredited supplier..."

  Added empty state warning below the dropdown:
    "No accredited suppliers yet. Go to Suppliers page and verify a
     supplier first." (shown only when supplier list is empty)

RESULT:
  Only accredited suppliers appear in the dropdown. Users get immediate
  feedback if no accredited suppliers exist, rather than a cryptic API error.
