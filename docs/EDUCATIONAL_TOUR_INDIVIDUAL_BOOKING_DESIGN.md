# Educational Tour: Package-Based, Per-Head, Individual Booking Design

## Decision

Educational Tours must be sold as a scheduled **package with a fixed price per participant**, not as a whole-bus sale.

- One package represents the school-specific tour offer, dates, itinerary, inclusions, price, and overall capacity.
- One participant entered by authorized JVD staff creates one booking reference and one invoice/billing statement.
- Payments belong to that participant booking and may be full, down payment, or installment payments.
- Buses belong to the package's operational plan. A participant booking may occupy one seat on one package bus, but the bus is never the billing unit.
- Vehicle/driver reservations and trip tickets are generated per package bus, not per participant invoice.

The existing `educational_tour_programs` table can remain as the reusable catalog/template. A new `educational_tour_packages` row is the dated, school-specific offer created from a program. The existing group-style `educational_tour_bookings` flow should become legacy/read-only after migration; new desk bookings use `educational_tour_participant_bookings`.

This rollout is desk-operated. No public registration page, shareable package link, booking statement link, or unauthenticated Educational Tour endpoint is exposed.

## Current gap

The current flow stores the school, dates, total student count, price calculation, one invoice, and all assigned buses in one `educational_tour_bookings` row. It therefore behaves like:

```text
one school group -> one group booking -> one invoice -> many buses
```

The required flow is:

```text
one scheduled package -> many participant bookings -> one invoice per participant
                      -> many package buses -> one seat assignment per confirmed participant
```

### Important accounting rule

`invoices`, `collections`, and immutable `collection_payments` remain the accounting source of truth. A posted educational-tour payment must be written atomically with its `collection_payments` row and linked through `collection_payment_id`. Do not update `invoice.amount_received` or `invoice.balance` independently; use the existing collection recalculation/sales-order synchronization path.

`educational_tour_booking_payments` provides the participant-facing payment history, payment-intent status, installment metadata, and direct booking relationship. It does not replace the general ledger or refund workflow.

## Capacity and allocation invariants

Database checks cannot safely enforce a capacity that depends on counts from other rows. Booking creation/confirmation must use one database transaction:

1. Resolve the package by opaque registration token plus `tour_code`; never trust a client-supplied price or package ID on the public endpoint.
2. Lock the package with `SELECT ... FOR UPDATE`.
3. Expire stale unpaid holds and clear their `bus_assignment_id`/`seat_number`.
4. Count capacity-consuming bookings: `pending_payment`, `partially_paid`, and `confirmed` whose holds are still valid.
5. Reject with `409 PACKAGE_FULL` when that count is already `maximum_capacity`.
6. Copy `rate_per_head`, VAT treatment, and payment terms into the booking/invoice snapshot.
7. Create the participant booking, its unique invoice, invoice item (`quantity = 1`), collection, and optional payment schedule in the same transaction.
8. For a paid/confirmed slot, lock active package bus rows in `sequence_number` order and select the first bus whose active assigned-seat count is below `capacity_snapshot`.
9. Assign the first free seat atomically. If there is no configured bus capacity, leave the participant on the package wait-for-allocation queue and alert Operations; never change the participant price.

Default allocation strategy: **fill the current bus first, then open the next bus**. Operations may rebalance participants before dispatch, but every move must keep `(bus_assignment_id, seat_number)` unique and must not alter any invoice.

Package capacity and physical bus capacity are deliberately separate:

- Package capacity controls whether another registration may be accepted.
- Sum of active bus `capacity_snapshot` values controls whether confirmed participants can be physically seated.
- Publishing should warn when planned bus capacity is below package capacity. Confirmation should block or queue allocation if there is no physical seat.

Payment validation rules:

- A posted payment is append-only and immutable.
- Sum of posted payments cannot exceed the invoice balance unless the existing overpayment/change workflow explicitly handles it.
- Full payment must equal the current balance.
- A down payment must meet the package minimum and be less than the total.
- Installment numbers and due dates come from the invoice's `payment_schedules`; the client cannot redefine them.
- Reversal/refund uses the existing approved credit-note/refund workflow, never an edit or delete.

## Status transitions

```text
Package: draft -> published -> registration_closed -> in_progress -> completed
                  \-----------------------------------------------> cancelled

Booking: pending_payment -> partially_paid -> confirmed -> completed
             |                  |                |
             +-------> expired  +--------------> cancelled
             +----------------------------------> cancelled

Payment: initiated -> pending -> posted
              |          |
              +--------> failed
posted -> refunded only through the approved refund workflow
```

A `pending_payment` slot should have a configurable expiration. A posted qualifying down payment removes the expiry and changes the booking to `partially_paid`; full settlement changes it to `confirmed`. If JVD wants registration without immediate payment to remain indefinitely, make that an explicit package policy rather than silently overbooking.

## Laravel refactor map

1. Keep `EducationalTourProgram` as the undated reusable template/catalog.
2. Add `EducationalTourPackage`, `EducationalTourParticipantBooking`, `EducationalTourBookingPayment`, and `EducationalTourBusAssignment` models and relationships.
3. Split the current `EducationalTourBookingService` into:
   - `EducationalTourPackageService` for package publication and fleet planning.
   - `EducationalTourRegistrationService` for capacity locking, individual booking, invoice creation, and idempotency.
   - `EducationalTourPaymentService` for collection posting and booking/payment status synchronization.
   - `EducationalTourBusAllocator` for fill-first assignment/rebalancing.
4. Stop accepting `student_count`, `assignments`, `amount_received`, and group pricing in the individual registration request.
5. Create an invoice item with `quantity = 1` and `unit_price = package.rate_per_head` for every participant booking.
6. Generate the participant's SOA from that booking's unique invoice. The package manifest aggregates participants across bookings.
7. Move resource reservations, work orders, and trip-ticket generation from the participant invoice path to package bus assignments. One bus assignment may create one DTT; 100 participant invoices must not create 100 DTTs.
8. Retain the existing `ResourceAllocationService` checks when a package bus/driver is reserved.
9. Add public routes outside `auth:sanctum` only for token-scoped package registration and booking self-service. Hash tokens, rate-limit requests, validate upload MIME/content if documents are later added, and never return another participant's data.
10. Mirror RBAC using split action groups: `sales:view` for package/booking reads, `sales:create` for package publication/registration, `sales:edit` for bus allocation/payment corrections through approved workflows, and `sales:delete` only for deactivation/cancellation entry points.

## Migration of existing data

- Convert each existing group `educational_tour_bookings` row into one package using its program, school, dates, pickup, stops, and price snapshot.
- Convert each `educational_tour_vehicles` row into a package `educational_tour_bus_assignments` row.
- When the legacy `passengers` JSON contains reliable named students, stage one participant booking per student for review.
- Do not fabricate participant identities from `student_count` alone. Flag those packages for roster import.
- Do not automatically split a paid/partially paid group invoice into individual invoices; doing so can duplicate recognized revenue and corrupt payment allocation. Preserve the old invoice as a legacy school/group settlement, or have Accounting approve an explicit allocation plan before creating participant balances.
- Keep old group records and documents readable. Route all newly published packages to the new endpoints.
- After reconciliation, remove the group checkout UI and label legacy records as `Legacy group booking`.

## Acceptance criteria

- Creating a package does not create a sale or invoice.
- Registering 60 students produces 60 booking references and 60 invoices, each billed at the package's one-head price.
- A second request with the same idempotency key returns the original booking and never consumes another slot.
- The 151st capacity-consuming registration for a 150-person package receives `409 PACKAGE_FULL`.
- Full, down payment, and installment payments update only that student's collection, invoice balance, and booking payment status.
- Cancelling/expiring a booking releases its package slot and bus seat without changing other participants' invoices.
- Bus 1 fills to its capacity before Bus 2 under the default allocator.
- A participant can be moved between buses without changing their booking amount or payment history.
- Package manifest totals equal active participant bookings, and each active participant appears at most once.
- Trip tickets/work orders are created per package bus assignment, not per participant booking.
- Public registration tokens cannot enumerate packages, bookings, invoices, or other participants.
